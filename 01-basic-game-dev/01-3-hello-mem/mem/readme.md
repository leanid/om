# mem — hello world с собственной системой памяти (Linux-only)

> Часть 2 трилогии `01-3-hello-mem`: `layout/` — карта памяти процесса,
> **mem/** — запрет new/malloc и свой аллокатор, `libs/` — запрет vs
> статические и динамические библиотеки.

Учебный пример «как в больших движках» (по мотивам `AzCore/Memory` из
O3DE): вся куча программы идёт через свой аллокатор, а стандартные пути
выделения памяти запрещены.

## Что делает пример

1. **`om::mmap_allocator`** (`memory.hxx` / `memory.cxx`) — обёртка над
   `mmap(2)` / `munmap(2)`. Перед указателем пользователя хранится
   16-байтный заголовок `{ mapping_base, mapping_size }`, поэтому
   `deallocate` знает, что именно отдать в `munmap`. Ведётся статистика
   на атомиках: счётчики аллокаций/деаллокаций и байт — упрощённый аналог
   трекинга аллокаторов в O3DE.
2. **`om::mmap_memory_resource`** — `std::pmr::memory_resource` поверх
   этого аллокатора. Через него легально работают `std::pmr::string`,
   `std::pmr::vector` и т.д.
3. **Глобальные `operator new` / `operator delete`** переопределены
   (все варианты: массивы, `std::align_val_t`, sized-delete, `nothrow`).
   Выделяющие версии пишут сообщение в stderr и бросают
   `std::bad_alloc`, nothrow-версии возвращают `nullptr`. Наши
   определения сильнее weak-символов из libstdc++, поэтому линкер берёт
   именно их.
4. **`malloc` / `free` / `calloc` / `realloc` / `aligned_alloc` /
   `posix_memalign`** переопределены: символы из исполняемого файла
   интерпозируются поверх libc для всего процесса. Возвращают `nullptr`
   (для `posix_memalign` — `ENOMEM`), т.е. пользоваться ими невозможно.
5. **hello world** переписан без стандартной библиотеки вывода:
   `std::cout` и `printf` могут внутри звать `malloc`, поэтому печать —
   напрямую через `write(2)`, числа — через `std::to_chars` в стековый
   буфер.

## Ключевые детали и грабли

- **Почему исключения вообще работают?** `__cxa_allocate_exception`
  сначала пробует `malloc`/`aligned_alloc`, а получив `nullptr`,
  откатывается на аварийный статический буфер (emergency buffer в
  libstdc++/libc++abi). Поэтому наш `std::bad_alloc` из запрещённого
  `new` успешно долетает до `catch`. Побочный эффект — при каждом броске
  в stderr видно `banned: aligned_alloc` (так зовёт libc++abi; в
  libstdc++ это был бы `malloc`).
- **`free` — нооп**, и это безопасно: раз `malloc` всегда возвращает
  `nullptr`, освобождать нечего (кроме `free(nullptr)`, что и так нооп).
- **SSO**: короткий `std::string("hi")` может *не* аллоцировать
  (small string optimization) и потому не упасть. Для демонстрации
  запрета в `main.cxx` используется длинная строка.
- **Запрет на уровне линковки, а не компиляции**: чужой код в .so тоже
  попадёт в наши `malloc`/`new`. Внутренности glibc при этом не ломаются
  — она зовёт скрытые `__libc_*` версии.
- **Elision new-expression**: компилятор вправе целиком выкинуть
  вызов заменяемого глобального `operator new` из new-expression,
  предоставив хранилище сам (например, на стеке) — `[expr.new]/13`.
  clang на `-O3` активно этим пользуется: `new int(42)` с не
  «убегающим» указателем вообще не доходит до нашего оператора!
  Поэтому в демо (пункты 4-5 в `main.cxx`) оператор вызывается напрямую
  как функция — такой вызов оптимизатор выкинуть не может. Учтите это,
  если будете проверять подмену `new` в своих проектах.
- **Heap-to-stack для malloc**: на `-O3` LLVM заменяет `malloc` на
  `alloca`, если указатель не убегает, — и проверка `p == nullptr`
  вырождается в `false` без всякого вызова. Поэтому в пунктах 6-7
  указатели прогоняются через `om::detail::opaque_escape()` — пустую
  функцию из другой единицы трансляции, которая для оптимизатора
  «непрозрачна» и заставляет аллокацию реально произойти.
- `mmap` всегда возвращает странично-выровненную память, но для
  поддержки произвольного `alignment` (в т.ч. `alignas(64)`) указатель
  дополнительно выравнивается вручную, а заголовок кладётся вплотную
  перед ним.

## А как этот вопрос решают большие движки

Наш пример — это «максималистский» подход: тотальный запрет. Реальные
движки так не делают, потому что они линкуют third-party (PhysX, Qt,
AWS SDK...), который честно использует `new`/`malloc`, и собираются с
выключенными исключениями. Вместо запрета — перехват и наблюдаемость:

| | наш `01-3-hello-mem` | O3DE (`AzCore/Memory`) | Godot (`core/os/memory`) |
|---|---|---|---|
| Подход | тотальный бан | перехват + тегирование | соглашение (`memnew`/`memdelete`) |
| Базовый аллокатор | `mmap` напрямую | `OSAllocator` → `SystemAllocator` (HPHA) → child-аллокаторы | обычный `malloc` + заголовок |
| Глобальный new/delete | переопределены: throw/nullptr | opt-in перехват через `NewAndDelete.inl` | не тронуты; свои placement-формы с тегом |
| Защита от случайного `new` | всё падает на линковке/рантайме | `AZ_CLASS_ALLOCATOR` в классе прячет global new для типа | нет механической; raw new работает, но вне трекера; code review |
| Контейнеры | `std::pmr` + свой resource | `AZStd` с аллокаторами | свои `Vector`/`CowData`/`HashMap` на `memalloc` |
| Трекинг | счётчики + заголовок | AllocationRecords: стеки, теги подсистем, `sys_DumpAllocators` | счётчики байт в DEBUG + profiler-хуки; `ObjectDB` ловит утечки при выходе |
| Исключения | есть (`bad_alloc` долетает) | нет (`-fno-exceptions`) | нет (`ERR_FAIL*`-макросы) |

Интересные детали:

- **O3DE**: глобальный new не переопределяют намеренно — цитата из
  `Memory.h`: *"By default AZCore doesn't overload operator new and
  delete. This is a no-no for middle-ware."* Вместо этого каждый класс
  несёт макрос `AZ_CLASS_ALLOCATOR(Class, Allocator)`, чей class-scoped
  `operator new` прячет глобальный для этого типа: даже сырой
  `new EngineClass` идёт в AZ-аллокатор. А модуль, желающий перехватить
  *весь* свой new, один раз инклюдит `NewAndDelete.inl` — готовые
  глобальные операторы, маршрутизирующие всё в `SystemAllocator`.
- **Godot**: ближе всех к нашему примеру по устройству — один плоский
  аллокатор-обёртка над `malloc` с заголовком перед указателем (размер +
  число элементов массива, поэтому `memarr_len()` знает длину массива
  по указателю). `memnew(T)` = `::new (DefaultAllocator{}) T` —
  placement new с фиктивным тегом, выбирающим их перегрузку. Глобальный
  new сознательно не трогают: сырой `new` работает, просто невидим для
  трекера; контроль — только code review.
- **Общее у всех троих**: заголовок перед указателем пользователя и
  счётчики аллокаций — та же схема, что в нашем `mmap_allocator`.
