# libs — запрет new/malloc vs библиотеки (Linux-only)

> Часть 3 трилогии `01-3-hello-mem`: `layout/` — карта памяти процесса,
> `mem/` — запрет new/malloc и свой аллокатор, **libs/** — запрет vs
> статические и динамические библиотеки.

Что будет, если процесс запретил глобальные `new`/`malloc` (как в
`../mem/`), а память выделяет **чужая библиотека**, слинкованная разными
способами? И какие сегменты появляются в карте процесса при подгрузке
`.so`?

## Устройство примера

- `greedy_lib/` — «чужая» библиотека (не знает о запрете) с четырьмя
  способами выделения памяти: глобальный `new`, `malloc`, прямой `mmap`
  и собственный статический пул в `.bss`. Собирается в двух видах:
  `greedy-lib-static` (`.a`) и `greedy-lib-shared` (`.so`).
- `banned.cxx` — тот же запрет `new`/`delete`/`malloc`/..., что в
  `../mem/memory.cxx`, плюс печать через `write(2)` без кучи. Запрет
  семейства `malloc` переключаемый (`om::set_malloc_ban`) — нужен для
  демонстрации `dlopen`, см. ниже.
- `maps.cxx` — чтение `/proc/self/maps` в статические буферы (куча
  запрещена!), diff снимков «до/после», поиск сегмента по адресу.
- `app_linked.cxx` — один и тот же main для двух таргетов:
  `01-3-mem-libs-static` (линковка с `.a`) и `01-3-mem-libs-shared`
  (load-time `.so`).
- `app_dlopen.cxx` — `01-3-mem-libs-dlopen`: грузит ту же `.so` через
  `dlopen` в рантайме и показывает diff карты памяти.

## Главный вывод примера

**Запрет — процессно-глобальный, и способ линковки библиотеки его не
обходит.** Во всех трёх вариантах поведение одинаковое:

| Способ в библиотеке | Результат под запретом | Почему |
|---------------------|------------------------|--------|
| `new`               | `std::bad_alloc`       | наши strong-символы перекрывают weak-версии libstdc++/libc++; исключение свободно пересекает границу `.so` |
| `malloc`            | `nullptr`              | интерпозиция: символ `malloc` из исполняемого файла стоит в глобальной области видимости динамического линкера раньше libc |
| `mmap`              | работает               | запрет — на уровне библиотечных функций (C/C++ API), а не системных вызовов |
| свой статический пул | работает              | куча не нужна вообще — так third-party код выживает под запретом |

Для `dlopen` всё то же самое: `RTLD_LOCAL` (по умолчанию) влияет лишь на
то, попадают ли символы самой `.so` в глобальную область, а разрешение
**не**разрешённых символов библиотеки всё равно идёт через глобальную
область — где первым стоит наш исполняемый файл.

## Сегменты, которые добавляет `.so`

- **load-time** (`01-3-mem-libs-shared`): сегменты
  `libgreedy-lib-shared.so` видны в карте уже на входе в `main` — их
  отобразил `ld.so`. Обычно это 4 mapping'а: `r--p` (relro/eh_frame),
  `r-xp` (код), `r--p` (rodata), `rw-p` (data + bss).
- **dlopen**: те же сегменты появляются в рантайме — пример печатает
  diff `/proc/self/maps` до и после `dlopen`, а затем исчезнувшие
  сегменты после `dlclose`.
- Указатель из `greedy_pool` для статической библиотеки живёт в сегменте
  **исполняемого файла**, а для `.so` — в `rw-p` сегменте самой
  библиотеки: пример печатает сегмент-владелец указателя.

## Грабли, на которых построен пример

- **Почему `banned.cxx` не в статической библиотеке?** Из `.a` линкер
  вытаскивает объектник только ради неразрешённых символов, а
  `malloc`/`operator new` уже «разрешены» из libc/libstdc++ — запрет
  молча не попал бы в бинарь. Поэтому `banned.cxx` компилируется прямо в
  каждый исполняемый файл.
- **Почему `dlopen` под запретом падает?** Начиная с glibc 2.35, `ld.so`
  после старта процесса пользуется интерпозируемым `malloc` (раньше у
  него был полностью отдельный аллокатор). Поэтому под тотальным
  запретом `dlopen` возвращает `NULL` с «out of memory» — пример это
  показывает, а затем на время загрузки ослабляет запрет
  (`om::set_malloc_ban(false)`): в этом окне `malloc` уходит в настоящую
  кучу через `__libc_malloc` — те же функции glibc, минуя интерпозицию.
- **Почему исключения работают?** `__cxa_allocate_exception` при
  неудаче `malloc` откатывается на аварийный статический буфер
  (подробности — в `../mem/readme.md`).

## Сборка и запуск

```sh
cmake --build build/ninja-llvm --config Debug \
    --target 01-3-mem-libs-static 01-3-mem-libs-shared 01-3-mem-libs-dlopen
ctest --test-dir build/ninja-llvm -R mem_libs --output-on-failure
```
