# layout — из чего состоит память процесса (Linux-only)

> Часть 1 трилогии `01-3-hello-mem`: **layout/** — карта памяти процесса,
> `mem/` — запрет new/malloc и свой аллокатор, `libs/` — запрет vs
> статические и динамические библиотеки.

Минимальный пример: программа сама, изнутри, показывает все свои
сегменты памяти — адреса, права доступа и то, как каждый вид памяти
инициализируется.

## Что показывает пример

1. **Где что лежит.** Адреса: кода (функция), строковых литералов и
   `const`-данных (`.rodata`), инициализированных глобалов (`.data`),
   неинициализированных глобалов (`.bss`), текущего конца кучи
   (`sbrk(0)`), куска `mmap`, функции из libc, локальной переменной
   (стек) и `environ` (верх стека). Каждый адрес сопоставляется со
   строкой `/proc/self/maps` — видно имя сегмента и его права
   (`r-xp`, `rw-p`, ...).
2. **Символы линкера `etext` / `edata` / `end`** — границы сегментов,
   которые линкер (и GNU ld, и lld) добавляет в каждый исполняемый
   файл. `end` — это стартовое значение program break.
3. **Как инициализируется память:**
   - `.bss` ядро обнуляет при загрузке (в файле хранятся только размеры);
   - `.data` читается из исполняемого файла;
   - свежая память от ядра (`mmap`, рост через `sbrk`) всегда нулевая —
     иначе сквозь неё утекали бы данные других процессов;
   - переработанная куча **не** обнуляется: `malloc` после `free`
     возвращает тот же chunk со старыми байтами;
   - стек **не** обнуляется: локальный массив содержит остатки
     предыдущего вызова функции.
4. **`sbrk` вживую**: сдвигаем program break на +1 MiB, трогаем память,
   возвращаем обратно.
5. **Стек растёт вниз**: адреса локальных переменных убывают с глубиной
   рекурсии.
6. **Вся карта на одной прямой** (финал): горизонтальная схема всего
   адресного пространства во всю ширину терминала — от zero page до
   памяти ядра, с реальными адресами этого запуска и объяснениями:

   ```
   0x0                                                           0xffffffffffffffff
   Z──────E────H~~~~~~~~~~~~~~~~~~~~~~~~~~M────────V──────S─────U~~~~~Y~~~~~~~~~K──
   ```

   Порядок сегментов верный, расстояния условные (при 2⁶⁴ адресов
   честный масштаб бессмысленен). `~~~~` — гигантские дыры несмапленных
   адресов. Легенда под прямой объясняет каждую точку:

   - `Z` — **zero page**: первые 64 КиБ закрыты полностью
     (`PROT_NONE`, `mmap_min_addr` = 65536) — разыменование `nullptr`
     падает мгновенно, а не читает мусор;
   - `E` — сегменты нашего exe, `H` — `[heap]`, `M` — mmap-область
     (наши `mmap` + все `.so`), `S` — `[stack]`;
   - `V` — **`[vvar]`/`[vdso]`**: вспомогательные страницы, которые ядро
     отобразило в наше адресное пространство (данные времени и код
     `clock_gettime`/`getpid` без перехода в ядро);
   - `U` — потолок user space `0x7fffffffffff` (128 ТиБ при 48-битной
     трансляции);
   - `Y` — `[vsyscall]`: legacy-страница на фиксированном адресе
     `0xffffffffff600000` (без ASLR), формально уже в половине ядра;
   - `K` — **старшая половина: память ядра** — из user mode недоступна,
     в maps не показывается; там ядро хранит остальное о процессе
     (`task_struct`, таблицы страниц, дескрипторы).

## Сборка и запуск

```sh
cmake --build build/ninja-llvm --config Debug --target 01-3-mem-layout
./build/ninja-llvm/01-basic-game-dev/01-3-hello-mem/layout/01-3-mem-layout
ctest --test-dir build/ninja-llvm -R check_mem_layout
```

## На что смотреть в выводе

- Адреса при каждом запуске разные — это ASLR/PIE.
- `r-xp`-сегмент с путём к бинарю — это `.text` + `.rodata`;
  `rw-p` — `.data` + `.bss`.
- `[heap]` появляется после первого `malloc` (glibc растит main-арену
  через `brk`); большие аллокации glibc отдаёт через `mmap` — они в
  `[heap]` не попадают.
- Библиотеки (libc и др.) видны в карте как отдельные группы по 3-4
  сегмента — подробнее об этом в `../libs/`.
